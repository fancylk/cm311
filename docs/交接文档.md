## 四、桌面问题（✅已解决 2026-09-20，黑屏真相见下）
- 原乐家桌面 com.xinjing.launcher（横幅丑）→ 已 `pm disable` 禁用；**KISS 是现在唯一也是默认的桌面**
- **黑屏真相：不是渲染问题，是 KISS 静默崩溃（桌面崩溃不弹对话框）**
  - 这台 ROM **砍掉了联系人提供器**（无 com.android.providers.contacts 包，com.android.contacts 权限节点不存在）
  - 且 ROM **自动授予所有运行时权限**（dumpsys 里 KISS 所有请求权限都是 granted=true；`pm revoke` 撤销后会被刷回来，别再浪费时间试）

- **修复（已验证有效）**：给 KISS 偏好文件加 `enable-contacts=false`，让 KISS 自己不去启动联系人服务：
  ```
  adb shell "sed -i 's|</map>|    <boolean name=\"enable-contacts\" value=\"false\" />\n</map>|' /data/data/fr.neamar.kiss/shared_prefs/fr.neamar.kiss_preferences.xml"
  # 之后 force-stop 重启 KISS（或重启盒子）
  ```
  - 偏好文件由 root 全新预置（仅一行 enable-contacts=false），首启即生效，无需等 KISS 先跑一次

- 截屏知识：这台盒子 screencap 出来桌面类应用是 1080x1920 竖幅（乐家也这样），电视上显示正常，不是问题；RustDesk 截屏是 1920x1080 横幅（它自己锁横屏）

## 二十七、CSD 喂参逆向破案：三个代码 bug 修复 + 固件实时输出门控定论（2026-09-23 下午，Mac 会话）

> 接续 §二十六续2 的主攻方向（逆向 goke 私有 CSD 喂参）。结论先行：**CSD 喂法问题已破解并修复，但固件在 MediaCodec 之下还有一道"实时输出门控"**——解码器 configure/CSD/喂帧全部正常，就是不吐帧，直到 EOS flush。验收目标（硬解 FPS≥12）在当前固件上通过标准 API 无解。

### 一、破案过程（NDK 演练程序对照实验，全部证据在盒 /data/local/tmp/ + Mac ~/rd_mc/goke_re/）
用 Swift+AVFoundation 生成 H264/HEVC 1280x720 测试流（gen_stream.swift，annexb 参数集分离导出），NDK 交叉编译 vdec_test.c 推到盒子直跑 MediaCodec，控制变量：
- **变体A**（参数集 flag=2 当 CSD + 全部帧正常喂）：✅出帧（首帧 ~1.9s，恰在 EOS 后）
- **变体B**（整个首包当 CSD，即 RustDesk 原行为）：✅出帧（参数集跨会话残留干扰，见下）
- **变体C**（完全不喂 CSD）：也"出帧"——但 AU0 里只有 SEI+IDR 无参数集，能解是因为 goke 服务端跨会话保留参数集（libgk_msp 字符串 `keep_spspps` 实锤），实验被污染
- **变体R**（RustDesk 式实时喂、不发 EOS）：❌ 8 秒零输出（HEVC 与 AVC、缓冲与 Surface 全部如此）
- **结论：goke 的 NDK MediaCodec 输出是 EOS/flush 门控的，实时会话永远等不到帧**。厂商播放器实时播放走的是 libgk_msp 的 avplay/nxplayer 私有管线，不经标准 OMX。

### 二、RustDesk 侧三个叠加 bug（本次全部修复）
1. **codec.rs dispatch 遮蔽（最致命）**：`handle_video_frame` 的 H264s/H265s 分支在 hwcodec 特性下排在 mediacodec 分支之前，Android 上 h265_ram 被前人 patch 置 None → 永远 `Err("don't support h265!")`，**mediacodec 解码分支是不可达死代码**。之前所有"MediaCodec 无输出"观测都含此 bug。修复：两个 hwcodec 分支加 `not(target_os = "android")`。
2. **CSD 喂入错误**：mediacodec.rs 用 `queue_input_buffer(..., 1)` 当 CODEC_CONFIG——NDK 语义里 1=KEY_FRAME，**2 才是 CODEC_CONFIG**（Java 层才是 1）！且首帧被双重入队、Surface 模式压根不喂 CSD。修复：annexb 参数集拆分（HEVC NAL 32/33/34，H264 7/8）→ flag=2 CSD（实测服务器流确实带内嵌 VPS/SPS/PPS，盒子日志 `csd queued: 84 bytes (flags=2)` + goke 接受）+ 两种模式都喂 + 不再重 Feed。

## 二十八、私有 vdec 实时输出突破（2026-09-23，进行中）

### 已证实的新发现
1. root shell 可直接加载 libgk_msp.so。初始化必须先调用 GK_SYS_Init（未调用时 AVPLAY_Init 报 GK_MODULE_Register param invalid）。最小创建链：GK_SYS_Init → GK_API_AVPLAY_Init → GetDefaultConfig(cfg,1/ES) → Create → ChnOpen(handle,2/video,NULL)。完整创建/销毁均返回 0。
2. GetDefaultConfig 写入 16 字节：{dmx=0,type=1,video_buf=0x1000000,audio_buf=0xc0000}。AVPLAY video attr ID=2，大小 0x24，默认 H264=4；HEVC=36（由库内 codec 名称表确认，35 是 MVC，错误选择会产生 stream errors）。LowDelay attr ID=11。
3. mpi_avplay_get_sync_vdec_handle(handle,&vdec,&sync) 返回 vdec=0x260000、sync=0x420000。GK_API_AVPLAY_Start 无 window 时返回 0x8031000a；直接 mpi_vdec_chan_start(vdec) 成功。
4. **H264 和 HEVC 私有通道均在不发送 EOS 时连续返回硬解帧**。喂入参数集和 90 AUs，每 AU 间隔 33ms；mpi_vdec_chan_get_buffer/put_buffer + mpi_vdec_chan_recv_frm/rls_frm。HEVC LowDelay=1/Bypass=1 时 AU0 后就有返回，直到 AU89；关闭两者仍持续返回。驱动证据 native_hevc36_off_proc.txt：HEVC(0x24)、1280x720、Lowdelay=0、Set EOS Flag=0、TotalStreamErrNum=0。这证明私有通路无需 EOS，但尚未完成 RustDesk 接入和性能验收。
5. mpi_vdec_set_low_delay → vdec_set_low_delay(0xb8ab4) → ioctl 0x400826b4；vdec_set_first_frame_bypass(0xb89ec) → ioctl 0xc00826e3。二者 payload={handle & 255, *value_ptr}，8 字节；本轮只操作自己创建的通道。LowDelay=1 实测 /proc/msp/vdec00 显示 1，但 AVPLAY proc 的 LowDelayEnable 仍 FALSE，不能把两个层的状态混同。
6. libstagefright 的字符串交叉引用将 ChannelAttributes 定位到 ACodec::BaseState::isRenderFrame（0x58d1c），获取扩展索引后通过虚表 +0x1c 调用，传 0x2c 字节结构；后续读取 +0x20 并做帧率/渲染节奏判断。当前证据是属性读取，不是已证明的 lowdelay 白名单下发。没有修改 /system 或 /vendor。
